# Task execution

Use this conditional procedure when briefing, executing, or accepting the tasks named in the trigger.
Firstmate selects and accepts delegated work; a worker executes its assigned scope.
A trivial prose edit or ordinary read-only factual question needs no feature map, benchmark, or new plan.
Keep selections and results in the existing brief or task report, outside the user's intent subsection.
Existing task authority and the selected No Mistakes path retain their lifecycle and review ownership.

## Select and drive product control

Start with the accepted caller action, observable good result, relevant side effect, and meaningful neighboring behavior.
Identify the actual revision, instance and data ownership, exclusive mutable resources, and proof destination before driving.
A clean worktree does not isolate ports, profiles, accounts, or shared UI instances.
Use the project's existing control recipes and tests first, even when its verification skill has a different name.
Read and follow the usable project-local verification skill for the changed journey.
If the necessary recipe is absent and creating it fits the assigned scope, explicitly read the available `kun-create-verification` skill and follow it to generate and prove a project-local recipe.
Discover that adapter through the session's skill catalog or installed skill location; explicit loading matters when model invocation is disabled.
If unavailable, use supported direct project commands and record the missing reusable recipe without silently installing a private dependency.
Do not claim full-map coverage from one convenient entry point.

Preserve failing-before evidence for a reproducible bug, replay the same discriminating user action on the candidate, and inspect the positive expected state as well as absence of the symptom.
A failed product expectation blocks that claim even when the tool exits successfully.
Retain action, outputs, side effects, revision, limitations, and proof after cleanup in the existing task report and selected validation path.
Missing prerequisites and untested entry points remain explicit.
The ordinary receiving task owner accepts evidence; this procedure adds no evidence validator or mandatory review gate.
For a plausible existing fix, use [diagnostic-reasoning](../diagnostic-reasoning/SKILL.md) before competing implementation.

## Maintain the recipe

After a relevant change, inspect and re-drive the affected recipe and impacted entry points in the same task, updating the local recipe only within assigned authority.
Report the exact targeted coverage.
An explicitly requested full-map audit explicitly loads available `kun-maintain-verification` and follows its every-feature source/live coverage and maintenance-only edit boundary.
If unavailable, disclose that limit rather than claiming the audit ran.
Distinguish recipe drift, a harness gap, and a product regression.
Never lower a valid expected behavior to hide a product failure or describe affected-feature maintenance as a full audit.

## Assign and receive teamwork

For a genuine authorized multi-worker need, name its purpose in the existing brief: coverage partition, competing alternatives, or review.
Name each assigned slice, shared acceptance, receiving owner, revision, expected evidence, and exclusive mutable resources.
Existing authorization chooses worker count, model, and effort; this skill neither spawns workers nor changes dispatch profiles.
Account for every required coverage slice, including blocked and missing results, before calling coverage complete.
Compare alternatives using the same task and data against a named uncertainty, retain the reason for selection, and verify the final combined artifact.
Product and architecture procedure owners retain substantive alternative selection; this skill owns assignment and receipt boundaries.
Route review through selected No Mistakes or a separately requested read-only audit, without a new panel or majority-vote acceptance.
A lone evidence-backed material finding remains actionable; a hypothetical preference does not automatically authorize a patch.
Serialize only truly shared mutable resources and keep one driver per shared UI instance.

## Bound measured work

For an actual measurable goal, record the metric and direction, realistic workload, baseline revision, correctness condition, finite attempt or effort boundary, and stop or pivot condition before experiments.
Confirm the evaluator detects wrong output, skipped work, and errors before optimizing.
Freeze that evaluator, test one named hypothesis per attempt, and retain comparable raw samples, environment, and rejected attempts.
An apparent improvement within observed noise is inconclusive; reject speed obtained by weakening correctness.
Reuse existing test-runner timing artifacts where applicable instead of creating a benchmark service.
Choose proportional sampling without a universal sample count, attempt minimum, latency SLA, or open-ended goal.
When decisions need a trail, explicitly load available `kun-evidence-log`, using a private task-owned path and one writer.
Otherwise the ordinary task report is sufficient; never introduce another task ledger.

## Checkpoint and continue

At a checkpoint or receiving handoff, consume the existing context capsule where available and retain consolidated accepted scope and latest correction, revision and uncommitted state, verified units and evidence, rejected attempts, owned resources, unfinished obligations, next executable action, and concrete boundary in the existing task record.
Reuse valid proof, rechecking changed prerequisites and unsupported inherited assertions.
Recall, knowledge placement, and general pickup policy remain with their existing owners.
Native turn recovery, dispatch advancement, and outcome delivery remain with continuity's runtime owners.
A finite boundary can end an episode with an honest incomplete result; retain the remaining obligation rather than inventing success.
