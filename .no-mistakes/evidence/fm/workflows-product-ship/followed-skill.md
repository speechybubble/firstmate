# Product experience

Use the accepted task, current correction, project references and existing evidence.
Put the primary user's action and observable result into the existing specification or task report.
Include the meaningful error and recovery path when it changes.
Respect the assigned role and current task authority, including held or cancelled work mentioned as context.
Keep intent separate from implementation acceptance; do not broaden the user's ask.
For a mechanical edit with a fixed target, skip exploration and retain the normal delivery path.
A routine task does not need a prototype, questionnaire or applicability report.

## Choose an interaction when the choice matters

Name the unresolved interaction choice before making variants.
Compare two or three materially different ways to complete the same action with the same content and starting state.
Different palettes of one interaction do not answer that question.
Resolve the existing Refero design skill through the available catalogue and use it for research, the reference lock, design-system constraints, accessibility and rendered review.
Preserve an approved fixed target rather than inventing alternatives or removing requested capability.
Compare sequentially as the assigned worker; this skill does not authorize an arena or additional agents.
Use the existing product control or verification recipe to observe entry, success, error, recovery and return behavior.
Record the observable trade-off, recommendation and why the other candidate loses in the current task record.
Separate visual target agreement, interaction correctness and product fit.
Screenshots show appearance; they do not establish task speed, satisfaction or successful keyboard behavior.
Route genuine new product choices through the existing owner and decision lifecycle.
Ordinary in-scope engineering choices need no renewed implementation permission.

## Make the first success usable

Choose the reader's task before the document form: learn a first success, perform a known task, look up a fact, or understand a mechanism or decision.
Use one short example if it answers that task; do not manufacture four documents.
For a caller interface, consume the realistic minimal caller example from the architecture owner.
Check whether the caller can reach its expected result rather than using a module diagram as evidence of usability.
Draft the minimal tutorial before final interface commitment and label unexecuted commands as proposed.
After implementation, run the example as written against the actual revision.
Inspect expected output and relevant failure/recovery behavior, then correct the tutorial or interface within the task's scope.
Do not invent API names or call plausible commands tested.
Architecture and API shape stay with their existing owner.

## Explain without changing the evidence

For a material handoff, explain the observed mechanism, supported reason for the choice, consequence and unresolved limit.
Reuse investigation evidence rather than spawning how/why workers or repeating history research for prose.
Distinguish observation, inference and unknown historical motivation.
Resolve existing writing owners through the available catalogue when applicable, including ASD-STE100 for technical clarity.
Preserve confidence, conditions, scope, values, necessary exact terms and evidence links when editing.
For example, “may have failed” cannot become “failed” to shorten a sentence.
A documentation audit is appropriate only when that owner's trigger applies, not for every handoff.

For staged persuasive or explanatory writing, identify what each stage contributes to the reader's task.
Each stage must add a fact, mechanism, consequence, objection response or next action.
Repeated benefits under new headings fail even if every file renders.
Revise duplicated stages or combine them when the chosen format permits it.
Marketing copy stays with the user's selected copywriting method and book preferences, not technical controlled language.
If required book/source material is unavailable, report the exact gap in that task without inventing content, claiming it was read, or installing a bundle.

## Demonstrate and hand off

Use the existing product recipe/control path and selected delivery validation.
Report the action, visible result, relevant side effect, revision and remaining limit.
Keep selected and rejected alternatives with the existing task record; use the existing learning owner for durable placement.
Use the existing control/feature-map owner for maintenance rather than creating a second map.
Do not add a ledger, scheduler, bot, mandatory review gate or delivery receipt.
A possible intake UI needs demonstrated repeated input friction and an assessment of the existing route before a proposal; this skill grants no endpoint authority.
Installation or a successful source check proves neither semantic judgment nor live adoption.
For a bounded synthetic exercise, use [experience exercise](references/experience-exercise.md); keep run-specific outputs and judgments in the private task report.
